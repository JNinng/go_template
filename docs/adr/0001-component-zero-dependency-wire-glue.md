# 组件零依赖模板，装配点显式胶水

组件是普通 Go module（可独立仓库），物理上无法依赖模板——模板是复制型资产，落地后每个项目的 import 路径都不同。模板也不约束组件的依赖：组件（尤其第三方库）依赖什么由其自定，模板不设限。引入组件只发生在装配入口（`internal/app/sources.go` 与 `biz.go`），以显式语句完成：`config.Decode`（读节）→ `New`（构造校验，fail-fast 点）→ `runner.Add`（注册生命周期）→ 可选 `config.Watch`（热更）。组件间依赖由装配点显式传参（类型化访问器 + 构造参数），依赖方向即书写顺序。

配套推论：

- 模板不存在注册表、容器、运行时发现机制——"组件约定"（DESIGN.md §11）是面向原生组件的文档形态，不是代码机制，更不是对组件的强制要求；第三方库保持原样，贴合发生在适配层。
- 装配辅助 `AddComponent`（模板侧泛型 + 结构化接口）把"解码（基座 Default）→ 构造 → 注册 → 可选热更"收敛为装配点一行；Go 结构化类型让组件零 import 即被识别，辅助是糖，手写展开始终等价可用。
- 组件拿配置的方式：app 侧解码后作构造参数传入；热更由 app 侧 `Watch` 解码后调 `ApplyConfig`。原生组件不接触配置树。
- "读自身配置节 + 订阅变更"的能力由模板侧 API（`config.Decode` / `config.Watch`）承担，组件零依赖因此无损失。

## Considered Options

- **发布极小"契约 kit"module**（配置树、订阅、生命周期接口所在地，模板与所有组件共同依赖）——拒绝：kit 与模板拷贝形成两个真相源；资产库从"模板+组件"两方膨胀为 kit/模板/组件三方；kit 的版本偏斜成为使用方永久负担。
- **复制型组件资产**（组件仓库 = 源码片段库，引入 = 拷目录进项目）——拒绝：放弃 bugfix 传播，资产随时间腐化；等价于放弃版本管理，把升级问题转嫁给逐项目的人肉复制。
- **组件直接依赖模板 module**——不可能：模板是复制型资产，落地后每个项目的 import 路径都不同，不存在可依赖的稳定路径。
